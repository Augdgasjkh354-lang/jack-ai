# 两条核心数据流：记忆检索、操作其他 App

照着真实代码梳理的，函数名都能在代码里搜到。目的是不靠 AI 也能讲清楚：数据从哪来、经过谁、存到哪、在哪一步兜底。

---

## 一、记忆：怎么记、怎么想起来

### 1. 存在哪

| 层 | 存在哪 | 谁写 | 每轮都带吗 |
|---|---|---|---|
| 常记（关于你本人） | `files/memories.json`（`Store.loadMemories`） | `save_memory`、聊天回看、夜间整理 | 带，进系统提示词，有预算 `MemoryOps.HOT_BUDGET` = 1500 token |
| 深处 | `files/deep_memories.json`（`MemoryOps.deep`） | 常记放不下时挪过来 | 不带，相关时才浮上来 |
| 作废的 | `memories_archive.json` | 整理时作废的 | 不带，只留档 |
| 历史版本 | `memories_versions/日期.json` | 每次大改前存一版 | 不带，能回退 |
| 本对话、项目记忆 | 对话文件夹里的 Markdown（`ChatMemory`） | `save_memory scope=chat/project` | 带 |
| 做事经验 | 共用的 Markdown（`ChatMemory.workFile`） | 做任务时学到的 | 带 |

### 2. 写进去：三个入口

```
① 聊天中 Kavi 主动记        ② 每聊 3 轮后台回看            ③ 每天凌晨 5:30 整理
   save_memory 工具             MemoryReview.review           Dreamer.dream（WorkManager）
   ToolSession.remember         后台模型看最近 8 条消息          看前一天全部聊天
   (tools/KnowledgeTools.kt)    最多改 3 条                     交一张「修改单」
        │                            │                              │
        └────────── 都在锁里改：Store.updateMemories / ChatMemory.update ──┘
                                     │
                         MemoryOps.apply 执行修改单
          （新增 / 修改 / 作废 / 合并 / 放到深处 / 拿回来，各带理由和出处）
```

- **① 主动记**：`remember` 先按设置判断能不能写全局（隐私项目、关了全局记忆就退回本对话），再在锁里读、改、写，别的对话同时在存也不会被旧数据盖掉。
- **② 回看**：`ChatViewModel.maybeReviewMemory` 在每次回答收尾后检查 `MemoryReview.due`（还没回看的用户消息 ≥ 3 条），到了就在后台跑一次。平常聊天写全局记忆，这几轮里列过清单的写做事经验。改了什么挂在回答下面告诉你。
- **③ 夜间整理**：模型不整份重写，只交修改单，由代码执行。一次动的已有记忆超过三成（`MemoryOps.tooMany`）就整次不做，第二天重来，免得一次改坏一大片。改前先存一版。

### 3. 想起来：每轮发消息时

```
你发消息
  │
  ├─ 常记：MemorySnapshots.get 拍快照（chat/MemorySnapshot.kt）
  │    同一个对话里不变 → 系统提示词开头一字不差 → 缓存命中
  │    重拍时机：对话被压缩 / 隔 2 小时没聊 / 你在界面上改了记忆
  │    → PromptBuilder.systemParts 放进系统提示词
  │
  └─ 深处：DeepRecall.note(你这句话)（data/memory/DeepRecall.kt）
       │  在 ChatViewModel.replyContextNote 里调，放在最后一条消息前面（每轮变，不影响前面缓存）
       │
       ├─ 关键词：MemoryOps.recall
       │    LibraryIndex 做 BM25（中文两字一组切词）
       │    过滤：至少共有 2 个「有分量的词」（去掉虚字、你的名字、「用户」）
       │
       ├─ 向量：DeepRecall.similarities
       │    Embedder.engines 按顺序试：硅基流动 bge-m3 → 手机本地模型（设置里能反过来）
       │    向量按「编号 + 文字指纹」缓存成 memory_vectors*.bin，文字改了才重算
       │    远程 6 秒超时，算不出来就只用关键词
       │    余弦相似度 ≥ 这个来源的门槛（bge-m3 是 0.6）才算想起来
       │
       └─ 合并去重 → 按相似度排 → 取前 6 条
            → 记一次「用到」（lastUsedAt、uses +1，夜里整理时常用的能回到常记）
            → 拼成【Also remembered】附进这轮
```

### 4. 资料库（RAG）：同一套检索，用在你导入的文档上

- 入口：`search_my_data` 工具 → `LibraryVectors.search`（`data/LibraryVectors.kt`）。
- 文档切成段落，建 `LibraryIndex`（BM25）。段落向量在后台慢慢补算（`LibraryVectors.kick`），存在 `files/library_vectors/`。
- 检索：关键词取前 30，向量取前 30（低于 `floor` 的丢掉），用 RRF 合并（`Facts.fuse`），取前 6 段。还没算好向量的段落只靠关键词，所以刚导入就能搜。
- 项目里超过 2 万字的资料（`PromptBuilder.PROJECT_INLINE_CHARS`）也走这条，不整份塞进上下文。

### 5. 要讲清的几个设计

- **为什么要快照**：DeepSeek 按开头一样的字算缓存。聊天中途新存一条记忆，如果马上改系统提示词，后面整段缓存全失效。所以新记忆马上写进文件，下一张快照才放进提示词。
- **为什么分常记和深处**：上下文有限，每轮都带所有记忆又贵又容易让模型分心。常记有预算，放不下的放深处，用得上的再浮上来。
- **为什么关键词、向量都要**：没配向量服务、断网时还能用；向量能找到换了说法的，关键词能找到专有名词。

## 二、操作其他 App：一次「点一下」怎么走完

### 1. 两条路

| | 主屏 | 后台虚拟屏幕 |
|---|---|---|
| 怎么开 | 设置里开无障碍 | 开无线调试并配对（Mika 模块） |
| 用户能干别的吗 | 不能，会抢屏幕 | 能，App 在看不见的第二块屏幕里跑 |
| 代码 | `a11y/KaviAccessibility.kt` | `a11y/BackgroundPhone.kt` + `mika/` |
| 统一入口 | `a11y/PhoneControl.kt`：同一轮任务固定用一块屏，后台出错不退回主屏 | 同左 |

### 2. 一次调用的链路

```
模型调 phone 工具（action=tap / type / read / steps ...）
  │
ToolSession.perform → dispatch → ToolSession.phone（tools/PhoneTools.kt）
  │
  ├─ 拿屏幕：ToolSession.claimPhone
  │    一个对话占着手机，别的排队；App 使用知识里标了「只能主屏」的不进虚拟屏幕
  │
  ├─ 检查 App：PhoneGuard.blocked（a11y/PhoneGuard.kt，纯规则，有单测）
  │    只能碰你在设置里勾过的 App；支付宝、银行、证券这类一律不碰
  │
  ├─ 读屏幕：svc.snapshot → ScreenText.elements → ScreenText.format
  │    无障碍控件树 → 清单「[编号] 类型「文字」」交给模型（和浏览器按编号点一样）
  │    控件树读不全：ScreenOcr 在手机上离线识别截图补字；模型能看图再附标号截图
  │    PhoneGuard.payPage：看到付款、输密码的字就停下
  │
  ├─ 动手前：check(screen, 按钮文字)
  │    PhoneGuard.risk：
  │      MONEY（付款）→ 不点
  │      ASK（发送、删除、提交、关注……）→ approve 弹窗问你（能选「以后都允许」）
  │      OK → 直接做
  │    beforeAction：按 App 的节奏规则（AppUsageNotes）控制间隔，像人一样慢一点，防风控
  │
  ├─ 执行：PhoneControl → KaviAccessibility
  │    tap：主屏优先发手势（带一点随机，像人手），不行再 performAction 点控件
  │    type：只填进输入框，不发出去；后台屏幕可以用剪贴板粘贴
  │
  └─ 做完：等界面停下（settle），再读一遍屏幕，把新清单作为结果返回
       → 模型看到新屏幕，决定下一步
```

### 3. 省步数的几种动作

- `steps`：一次交几步（打开 → 点搜索 → 输入），每步可带 `expect`，等那几个字出现再做下一步。哪步没成就停（`phoneSteps`）。
- `collect`：逐屏往下翻，把相邻两屏重叠的行去掉、拼好再返回（`PhoneCollect`）。
- `wheel`：时间、日期滚轮一次转到位（`PhoneWheel`）。
- 手机流程：做成一次后存成文字步骤加录下的动作，下次 `replay` 直接重放，对不上就停下交还给模型（`phoneFlow`、`phoneReplay`）。

### 4. 要讲清的几个设计

- **为什么给模型看文字清单，不只给截图**：便宜、快，不能看图的模型也能用；按编号点比按坐标点准。
- **为什么安全规则写在代码里，不写在提示词里**：模型可能被网页、聊天内容里的指令带偏，代码里的 `PhoneGuard` 不会。付款页、敏感 App 是硬拦。
- **为什么每步都重新读屏**：App 界面随时会变（弹窗、加载），按旧清单点容易点错。
