## 一、优先：签名密钥不该在仓库里

**依据**：`app/build.gradle.kts` 第 25–33 行，`storePassword = "jackai2026"`、`keyPassword = "jackai2026"` 是明文常量；`app/jack-ai.keystore` 本身也在仓库里；`.gitignore` 没排除它。

仓库是公开的。也就是说，**任何人现在都能拿到这个 keystore 和密码，签出一个包名 `com.jack.ai`、签名相同、安卓会当成正版升级的 APK**。自己一个人装着用，风险有限；一旦你把 APK 发给别人装，或者以后上应用商店，这就是一个实实在在的洞。

建议做法（按风险从低到高排）：

1. 密码改从环境变量读，GitHub Secrets 里存 `KEYSTORE_PASSWORD`、`KEY_ALIAS`、`KEY_PASSWORD`；本地构建时用 `local.properties` 兜底。
2. keystore 用 base64 存进 Secrets，CI 里解码到临时文件再签。仓库里删掉那 2KB 文件。
3. **注意**：这一步做完，`main` 里那个keystore 已经被公开过了，安全上等于作废。如果你只自己用，改密码+移出仓库就够；如果要分发给别人，应该重新生成一个 keystore——代价是已安装的用户必须卸载重装，聊天记录得先「备份」成 zip 再导入。
4. 顺带：`isMinifyEnabled = false`，包体和符号表都是全裸的。开 R8 要配 keep rules（kotlinx.serialization、Chaquo、WebView JS 桥都要），属于可选项，不急着动。

## 二、内置技能的说明文字应该搬出代码

**依据**：`data/Skills.kt` 427 行、64KB，里面 `BUILTIN_SKILLS` 是一整个 `listOf`，每条技能的 `instructions` 是 Kotlin 三引号长字符串（联网搜索、Word、PPT……全是）。

它占了整个仓库最大的体积，但只有 427 行——因为全是中文文本。问题不在行数，在于：

- 改一句提示词，就要重新打包、重新发版、用户重新下载。
- 内置技能在代码里、用户自建技能在文件里，两套存储，`SkillsScreen` 得同时伺候。
- 提示词没法单独测试、单独对比效果。

建议：`app/src/main/assets/skills/*.md`，每个技能一个文件（前面放一小段 front-matter 写 id、name、description、用到哪些工具），`Skills.kt` 只留读取和合并逻辑。收益立刻可见：调提示词不用发版，还能顺手做「内置技能的新版覆盖」——已经装了的用户下次启动就把新说明拉到本地。

## 三、两个大文件的拆法

`ChatScreen.kt` 969 行、`ChatViewModel.kt` 836 行。这两个我没逐行读，只说拆的方向，别当结论：

- **ChatScreen**：按屏幕区域拆成 `MessageList` / `InputBar` / `ToolActivity` / `TopBar` 几个 composable 文件，`ChatScreen` 只留布局和状态分发。Compose 里这属于纯收益，几乎没有风险。
- **ChatViewModel**：真正的风险在这里。它同时管流式接收、工具循环状态、上下文压缩、计价统计、附件、重试。建议先只抽一样出来——**计价与用量**最独立、最好搬，抽成 `UsageTracker`，被 ViewModel 依赖而不是写在里面。搬完跑一遍现有测试，能过就说明切干净了。
- 合并成一件事：**别为了拆而拆**。这两个文件目前还能读，动它们的唯一理由是「以后加功能会撞车」。如果你近期不打算大改聊天页，可以放着。

## 四、工具层还缺的两块（核过代码）

**表格**（`tools/TableTools.kt`）：只有建表、记一笔、按条件查、求和、改、删、删表。**没有排序、分组、按日期区间筛选、导出 xlsx**。日常记账够用，一旦用户问「上个月餐饮比上上个月多多少」「按类别排一下」，只能靠 AI 反复查再自己算——烧 token 还容易算错。这几个参数加在 `query_table` 上很便宜：`order_by`、`group_by`（带 sum/count）、`date_from`/`date_to`，导出 xlsx 可以直接复用 `OfficeWriter`。

**日历**（`data/CalendarTool.kt`）：只有 `insert` / `list` / `get` / `delete`，**没有 update**。所以「把周五的会改到周六」现在只能删了重建，编号会变，重复日程的例外规则也会丢。日历变更用 `ContentResolver.update` 很快，值得补。

**已经补上的、我原先以为还缺的**（免得重复劳动）：提醒和任务的 `replace` 参数已经有了（`ScheduleTools.kt:180`），日历也有 replace 分支；邮件那套 `uid` 跨文件夹删错信的问题，`MailSeen` + `folderOf` 已经处理得很干净，多文件夹冲突会主动报错要模型写明 folder——这段代码比大多数同类实现都稳。

## 五、做对了、别动的地方

- `MailTools.kt` 的 `folderOf`：模型不填 folder 时查历史、拿不准就报错。这是把「危险操作」和「模糊输入」隔开的正确姿势，比默认 INBOX 强太多。
- `LoopGuard.kt`：工具死循环的兜底，独立成文件、有测试。
- `scripts/check_office.py`：生成完 Office 文件后用 python-docx/openpyxl 回读校验。这个做法很少有人想到——生成文件最怕的是「文件能打开但是空的/结构坏了」，回读一遍才知道真的写进去了。
- CI 的报错提取（`build.log` 里 grep `^e:` 打成注释）：在手机网页上看失败原因，实用。
- 测试里用了 Greenmail 和 Robolectric：邮件和界面手势都能在 CI 里跑，不是摆设。

## 六、可以往后放

- `lintRelease` 加进 CI（现在只有单测 + Office 校验）。
- 界面文案没走 `strings.xml`，全硬编码在 Kotlin 里。只做中文一直没影响，要做多语言才需要动。

### 一、签名密钥 —— 同意，但要 Jack（用户）先拍板

- 核对：属实。`app/build.gradle.kts` 里是明文密码，`app/jack-ai.keystore` 在仓库里，仓库是公开的。
- 你没提到、但更要紧的一点：现在 App 里存着 GitHub 读写令牌、Notion 密钥、邮箱授权码、各家模型的 Key。有人拿这把钥匙签一个假 Jack，只要用户装上它，安卓会当成正常升级，数据就全归它了。所以这件事的分量比你写的还重。
